## Need 2 — judgment in the grey areas

**Coverage note:** Three parts of this need statement are already covered and are not restated above.

1. The determinism OUTCOME is CORE-210's - "the same top-5 candidate contract-vehicle list in >=95% of runs." I have not re-asserted reproducibility. CORE-283 refines CORE-210 by requiring the MECHANISM that makes it hold once policy-prior tie-breaking is added: CORE-210 says the answer must be stable, CORE-283 says no pair may be left for the filesystem or a dictionary to order. TP-283 deliberately reuses TP-210's 20-run shape.

2. Reporting a numeric confidence per candidate is already DATA-OUT-300's ("each candidate carrying a numeric confidence/score and the set of source documents that contributed to it"), and exists in code as CandidateVehicle.Score. CORE-280 does not restate that; it refines DATA-OUT-300 by adding the margin, which is the figure the flat-distribution case actually needs and which a bare score cannot express.

3. Producing a results visualization is already OUT-410's, and the bundle is already OUT-440's. CORE-288 proposes no new artifact; it refines OUT-410 by naming content that artifact must carry - the flagged near-tie and abstention items. If the SE prefers, CORE-288 could be folded into OUT-410 as an amendment rather than carried as a new row.

Partially covered in code but in no RTVM row: VehicleRecommender.cs already implements an explicit three-key tie-break (score, then contributing-document count, then ordinal VehicleId) with an inline comment citing CORE-210. That is the ladder CORE-282 and CORE-283 formalize and extend. It is an undocumented implementation convention today, traceable to no requirement, which is exactly the gap this block closes.

Not covered anywhere, in the RTVM or in the code: near-tie detection, policy-prior tie-breaking, abstention, and the new-strategic-vehicle-indicated path. There is no vehicle knowledge base in the codebase at all, so CORE-284, CORE-285 and CORE-287 describe behavior over data that does not yet exist.

**Tensions flagged:** 1. THE SINGLETON 1.0 CONVENTION BLOCKS VERIFICATION OF THIS WHOLE BLOCK. VehicleRecommender.ComputeCohesion returns 1.0 for any one-document cluster "by convention." On the real reference set, 11 of 20 documents were singletons, so today's ranked list opens with a plateau of eleven candidates at exactly 1.0 - an artificial tie group that CORE-281 would flag as the flattest possible distribution while being a pure scoring artifact. Near-tie detection cannot be meaningfully tested, and epsilon cannot be tuned, against a score column containing a spike of exact 1.0s. This block depends on that repair; the repair itself belongs to the scoring requirement, not here.

2. CORE-286 COSTS POINTS UNDER THE PUBLISHED RUBRIC. The challenge awards 2 points per correct prediction against PGIL's list of 20 and states no penalty for a wrong one. Under that scoring, abstaining has strictly negative expected value and guessing is free. The client should see this plainly: defensibility (references/ai-boundaries.md) and score (SN-1) point in opposite directions. Recommended resolution is to keep the abstention record but still emit the sub-floor candidates in a clearly separated "below evidence floor" section, so no scoreable prediction is discarded and no unsupported answer is presented as a recommendation. If the client prefers to maximize score, CORE-286 must be rewritten as a LABELLING requirement rather than a SUPPRESSION requirement - that is a client decision, not an engineering one.

3. CORE-284's SEAPORT PRIOR MAY LOWER MEASURED PRECISION WHILE BEING MORE DEFENSIBLE. Two audits of the reference set on 2026-09-04 found that no document in it was issued by a NAVAIR office and that neither of the two vehicles named in the corpus appeared in the ground-truth set. If PGIL's list of 20 does not reflect NMCARS 5237.102 the way a Navy services SME would, hard-wiring the prior moves candidates away from the scored answers. It should therefore be a configurable, documented rung whose effect is measured both ways in the CORE-260 comparison, not a compiled-in constant. CORE-284 also presumes an Annex 22 functional-area classification the pipeline cannot produce today: DocumentTypeClassifier.cs recognizes five categories by literal token match and otherwise returns Unknown, and IngestionRunner.cs builds each DocumentRecord from four fields only - no PSC, NAICS, contract number, office code or section structure is extracted at all.

4. CORE-284, CORE-285 AND CORE-287 REQUIRE A VEHICLE KNOWLEDGE BASE THAT DOES NOT EXIST. Ordering-period ends, Annex 22 scope text, office-affinity distributions from historical orders, and ceiling headroom must all sit inside the image under NFR-500 with no run-time network under NFR-510. That data pulls against CORE-220's 1-core/2GB/30-minute budget and against the image size DELIV-930's first-time evaluator has to build and pull. None of these three items is verifiable before that knowledge base lands; sequence them behind it.

5. TWO NEW TUNING CONSTANTS INHERIT A KNOWN FAILURE MODE. Epsilon (CORE-281) and F (CORE-286) are exactly the kind of constant that produced the 0.35 similarity threshold - derived from a synthetic ten-document fixture and wrong on real documents, where it left 11 of 20 solicitations as singletons. Both must be derived on the N=20 reference set and re-derived on GFI the day it arrives, with the derivation written into the algorithm documentation the way TfIdfCosineClusteringComponent documents 0.35 today (DELIV-970).

6. CORE-289 SITS AGAINST THE CHALLENGE'S OWN WORD "RECOMMENDATIONS." A reviewer can reasonably read a ranked list of vehicles as an originated recommendation, which is what the rubric asks for and what references/ai-boundaries.md constrains. The line drawn here is that the tool ranks evidence and names the rule it applied, and never writes the FAR 7.107 determination or asserts commerciality, set-aside or contract type. State that line explicitly in the submitted algorithm documentation, because a judge who does not see it stated may read CORE-289's caution as the tool declining to answer the question it was built for.

7. THE CORE-280..289 BAND IS FULLY CONSUMED by these ten items. Any further grey-area requirement - a per-cluster confidence-calibration item, or a separate requirement to log eliminated candidates with the check each one failed - needs a CORE-290+ block.

## Need 1 — compartmentalized SME agent / vehicle knowledge base

**Coverage note:** Genuinely already covered, not restated above:

- **"Compartmentalized" = offline and no LLM.** CORE-240 (zero LLM calls on the core clustering/recommendation path, by dependency and call-site inspection) and NFR-510 (zero outbound connections in default operation) already cover the "no fetching, no model" half of compartmentalization completely. I propose nothing on either point. NFR-500 (image bundles every runtime dependency, nothing fetched at run time) already covers the fact that the knowledge base must be *in* the image; KB-600 only adds the shape that artifact must take (version identifier + complete digest manifest), which NFR-500 does not speak to.
- **Determinism of the answer.** CORE-210 (same top-5 in ≥95% of runs) already covers reproducibility of the vehicle list, and NFR-520 covers replica-independence. Adding vehicle matching does not need a new determinism requirement; it needs the existing ones re-run. Flagged below as a tension instead.
- **The output being a ranked, scored list with contributing documents.** DATA-OUT-300 already requires "a ranked candidate contract-vehicle list per run, each candidate carrying a numeric confidence/score and the set of source documents that contributed to it." That shape exists and is Verified in code (`Naadap.Core/CandidateVehicle.cs`, `Naadap.Output/VehicleRecommender.cs`). CORE-270, CORE-271 and CORE-273 are marked as **refining DATA-OUT-300**, not replacing it: 270 constrains what the identifier may be, 271 constrains what must accompany the score, 273 constrains the ordering. None of them re-states the list-with-scores requirement.
- **A run manifest.** OUT-440 already requires one manifest file indexing the bundle, and `Naadap.Core/RunManifest.cs` implements it. CORE-275 refines OUT-440 with two named fields; it does not propose a manifest.
- **A cluster-to-vehicle visualization.** OUT-410 already requires "a visualization of the results (ranked candidate list / cluster-to-vehicle mapping)". Nothing proposed there.
- **Clustering itself.** CORE-200 covers grouping by shared acquisition-requirement content. Every requirement above consumes clusters; none re-derives them.
- **Documenting the method.** DELIV-970 (algorithm documentation as a discrete artifact) and OUT-430 (validation methodology) already carry the obligation to explain the matching method in prose. KB-620's per-field provenance is *not* covered by DELIV-920, which governs NuGet/third-party code dependencies, not vendored data.

Partially covered and deliberately left alone: OUT-420's summary metric. The vehicle-matching step changes what should be measured (per-document agreement with a human vehicle label, paired with a pairwise clustering measure), but that belongs to the validation need statement, not this one.

**Tensions flagged:** Seven, stated plainly. The first three are blocking.

**1. Half of these requirements are unimplementable against today's ingestion, and the gap is not mine to close.** `Naadap.Ingestion/IngestionRunner.cs` builds each `DocumentRecord` from four fields — filename, doc type, extracted text, date. There is no contracting-office DoDAAC, no PSC, no NAICS, no incumbent contract number, no period of performance, no set-aside, no section structure. CORE-271's `codes` and `office_affinity` channels and CORE-272's ordering-period and eligibility checks all read fields that do not exist. `DocumentTypeClassifier.cs` makes it worse: it recognizes five categories by literal token match and returns `Unknown` otherwise, so on the real reference set most documents arrive untyped. **Recommendation: CORE-271 and CORE-272 enter the RTVM as Draft/Blocked, blocked on a document-field-extraction requirement that belongs to whichever need statement covers ingestion depth.** If that extraction work is not scheduled, CORE-271 collapses to the lexical channel alone and CORE-272 to the ordering-period check alone — which is a weaker but still shippable subset worth saying out loud now rather than discovering in test.

**2. CORE-270 directly contradicts a Verified requirement's implementation contract.** `Naadap.Core/CandidateVehicle.cs` documents `VehicleId` as "not a lookup against a real-world contract-vehicle name/database, since the pipeline has no such reference data and CORE-240 forbids an LLM call to synthesize one," and `VehicleRecommender.BuildVehicleId` emits `CLUSTER-0001-FLIGHT-LINE-ENGINEERING`. That reasoning was sound when there was no knowledge base; with one, it is wrong, and the stated CORE-240 justification never applied — a vendored lookup table is not an LLM call. Adopting CORE-270 requires withdrawing that doc comment and `BuildVehicleId`, and DATA-OUT-300 (currently Verified, commit 6ec62ff) will need a note that its "candidate contract-vehicle" is now a real named vehicle. **This is a status regression on a Verified row, and the Systems Engineer should decide whether DATA-OUT-300 returns to In Implementation or carries a refinement note.**

**3. The `Score` field means two different things and CORE-273's 0.05 band depends on resolving that.** DATA-OUT-300's score is today cluster cohesion — mean pairwise cosine — and `VehicleRecommender.ComputeCohesion` returns 1.0 for a singleton "by convention," which puts every loose document above every real cluster and makes precision@5 measure filename order. CORE-271's composite is a weighted sum of vehicle-match channels: a different quantity on the same field, on a different scale. Either DATA-OUT-300's `Score` changes meaning (and the singleton-1.0 defect is fixed as part of that), or `CandidateVehicle` carries both a cohesion score and a match score. **Until that is decided, CORE-273's 0.05 tie band is a number against an undefined scale.** I have not proposed the singleton fix as a requirement here because it is a clustering defect, not a knowledge-base or matching one; it should be raised wherever clustering quality is being derived.

**4. Evidence richness pulls against CORE-220 and NFR-530.** The historical-orders channel in CORE-271 is the strongest predictor an SME uses ("has this office put similar work on that vehicle before"), and its source — the USAspending bulk contract archive — is hundreds of megabytes per fiscal year. A 1-core/2GB tier with a 30-minute budget cannot hold or scan that. **Mitigation to decide now, not at integration: vendor a pre-aggregated slice (top-k historical orders per vehicle, plus per-vehicle PSC/NAICS/office distributions already rolled up) rather than raw order rows, and state that cap in KB-610's schema.** If the client wants full order history, CORE-220 and the 1c/2GB scoring tier are in play, and SN-2 scores the low tier highest — so the cap is the right call, but it is a real loss of evidence and should be recorded as such in the algorithm documentation.

**5. A frozen, hashed knowledge base is deterministic and goes stale.** KB-600 and KB-630 make the artifact immutable per image; vehicle facts are not. `references/contract-vehicles.md` carries research date 2026-09-04 with several figures marked unconfirmed and several `.mil` sources blocked (seaport.navy.mil returned 503 throughout; navair.navy.mil and navsea.navy.mil returned 403). NAWCAD PSMI's ordering period is "not confirmed"; NIWC Pacific Cyberspace S&T's follow-on was not located. `kb_version` is a mitigation, not a fix. **The submission must state the knowledge base's as-of date and that ordering periods and ceilings require re-verification before operational use** — otherwise CORE-272 will confidently eliminate a vehicle on a stale `ordering_period_end`, which is a worse failure than not checking at all. Verified determinism and current facts are in genuine conflict; the honest resolution is a dated, versioned knowledge base plus an explicit currency caveat, which is what I have proposed.

**6. I deliberately did not propose the FAR 7.107-2 input fields, and that is a visible hole.** `references/vehicle-matching.md`'s output record includes `far_7_107_inputs` (estimated aggregate value, count of separate current contracts, benchmark rates, small-business impact). Two reasons for leaving them out: every one of them depends on data the pipeline does not extract (tension 1), and they sit closest to the reserved consolidation determination, which per `references/ai-boundaries.md` the SPE, CAO, DASN(P) or HCA makes and the tool never originates. **Recommendation: raise them under the extraction need statement, paired with an explicit negative requirement that no field of the output asserts consolidation is "necessary and justified."** CORE-274 flags the 7.107-1 *exemption* — a citation, not a conclusion — which stays on the safe side of that line, but the 7.107-2 inputs are the place where this tool could most easily cross it, and nothing above currently guards that boundary.

**7. Two ID-scheme notes for the Systems Engineer.** (a) I opened a new `KB` block at 600–699 for the four knowledge-base-artifact requirements, using the RTVM's own permission that "the category blocks below are a starting point — adjust them to fit the project." The justification: the vehicle knowledge base is a configuration-managed *data* artifact with its own version, provenance and integrity contract, and is itself part of the captured-SME-knowledge deliverable — it is not core algorithm code, and filing it under CORE mislabels it and consumes the whole assigned 270–279 band with no headroom for the matching work that will follow. The 600s are unused between NFR (500s) and DELIV (900s). If you reject the new block, these four map cleanly to CORE-277, 278, 279 and one overflow, but you will need a band extension. (b) Every existing RTVM ID is a multiple of ten; the assigned CORE-270..279 band is ten consecutive integers, so CORE-270 through CORE-276 necessarily break that spacing. I used consecutive numbering there because the band was specified that way, and decade spacing (600/610/620/630) in the new KB block where nothing constrained me. Worth normalizing one way or the other before these rows land.

One smaller flag, not a conflict: CORE-270's `NEW-VEHICLE-INDICATED` literal scores zero against PGIL's list of 20 by construction, since that list is of vehicles. It is still the right output when no existing vehicle can absorb a cluster — the challenge's problem statement is partly about exactly those requirements — but whether such entries should occupy a top-5 slot that could hold a scoreable guess is a scoring-strategy decision for the client, not an engineering one.

## Need 4 — multiple separate current contracts (FAR 2.101)

**Coverage note:** Three parts of this need statement are already covered and are not restated above.

(1) Grouping documents by shared acquisition-requirement content is CORE-200 (Verified). Nothing above re-asserts clustering; every row consumes a cluster CORE-200 already produced.

(2) "The set of source documents that contributed to a candidate" — what the need statement calls "members of the same cluster" — is already DATA-OUT-300 (Verified), implemented by DocumentCluster.DocumentFilenames and CandidateVehicle.ContributingDocuments. DATA-OUT-340 counts distinct contracts across that existing member list; it does not re-specify the list.

(3) Getting the consolidation record in front of a reviewer is already OUT-440's single manifest bundle (Verified), which DATA-OUT-310's withdrawal made the sole persistence path. No new bundling or persistence requirement is proposed; the fields above land in the existing RunManifest.

What is genuinely absent, and is why rows 320-385 exist: DATA-IN-100 (Verified) specifies the normalized record as exactly four fields — extracted text, document-type tag, source filename, date — and IngestionRunner.cs builds exactly that. No contract number, value, option period, PSC, NAICS, or office code is extracted anywhere in the codebase, so there is today no input from which any FAR 2.101 or FAR 7.107 fact could be computed. DATA-OUT-300 likewise specifies only "a numeric confidence/score" per candidate, and VehicleRecommender.ComputeCohesion computes that score as mean pairwise cosine cohesion — a similarity artifact, which is precisely what the client's "that's not a similarity artifact" is rejecting.

**Tensions flagged:** Six, none cosmetic.

1. DATA-OUT-350 contradicts shipped, Verified behavior. VehicleRecommender.ComputeCohesion returns 1.0 for any single-document cluster "by convention," so every singleton currently outranks every real cluster. A singleton can never carry two distinct current contracts, so DATA-OUT-350 removes exactly the clusters that today sit at the top of the list. This is a defect fix wearing a new-requirement label, and it changes output under DATA-OUT-300, CORE-210, and OUT-420 — all marked Verified. TP-210, TP-300, and TP-420 all need re-running, and the reported precision@5 will move.

2. DATA-OUT-320/330/360 push new fields into DATA-IN-100's record, which is Verified with a four-field shape written into DocumentRecord.cs's own doc comment. Either DATA-IN-100 is amended and re-verified, or these fields live in a second record produced by a later stage and DATA-IN-100 stops being the whole truth about a document. That is a Systems Engineer call, not one I can make here, but it cannot stay implicit.

3. Recall versus the client's purity. The client's framing is that the two-or-more-separate-contracts pattern IS the definition. But the SME's own audit of the 20-document reference set found only 2 documents naming any vehicle, and a sources-sought notice often names no incumbent PIID at all. Gate strictly on extracted contract numbers and the pipeline surfaces almost nothing on the reference corpus and scores near zero against PGIL's 20 — 2 points lost per suppressed candidate. DATA-OUT-350 therefore excludes only a confirmed count of 1, never a count of 0. That is a deliberate softening of the client's stated position and he should see it as such: absence of evidence is treated as unknown, not as disproof, and a count-of-0 cluster will still be ranked on similarity alone — the very artifact he is objecting to. If he wants the strict reading, DATA-OUT-350 changes to exclude 0 as well, at the recall cost above.

4. Thresholds versus NFR-500/NFR-510. $2,000,000 is statutory under 15 U.S.C. 657q and not inflation-adjusted, so it is safe in requirement text. $8,000,000, $94,000,000, and $9,400,000 are FAR 1.109 adjusted figures, last effective 1 Oct 2025 and due to move again. NFR-500 requires them vendored into the image and NFR-510 forbids fetching them at run time, so a container built today will silently emit a stale threshold after the next adjustment. Hence the effective-date field in DATA-OUT-375. Nothing inside these constraints makes it self-correcting; it is a rebuild obligation on the team.

5. DATA-OUT-360 versus CORE-240. Pulling "base year $900,000 plus four 12-month option periods" out of prose is what an LLM is good at and a regex is brittle at, and CORE-240 forbids an LLM anywhere on the core path. Expect this row to be the weakest link in accuracy, and expect its failures to propagate into all three FAR 7.107 flags. The mandated partial-coverage value basis is a mitigation, not a fix.

6. DATA-OUT-385 versus the need statement's own force. "Finding that pattern is the whole point" is correct about FAR 2.101, which is a definitional test on facts. But a record asserting that a cluster IS a consolidation is one adjective away from originating the determination FAR 7.107-2 reserves to DASN(P) or the HCA. Every label above is therefore worded as a precondition met, never as a determination made. If a future revision wants a plain "consolidation candidate: yes" field for Demo Day readability, that is a real trade against ai-boundaries.md and belongs in front of the client, not in an implementation ticket.

## Need 3 — distill pedantic documentation to the core need

**Coverage note:** Four existing items already carry part of this need statement, and I have not restated any of them.

DATA-IN-100 already owns the ingest-to-normalized-record step and already delivers four of the fields this need would otherwise ask for: extracted text, document-type tag, source filename, and date. Six of my ten proposals (130, 135, 155, 160, 165, 170) are refinements that add fields to that same record rather than new items; the record they extend is `src/Naadap.Core/DocumentRecord.cs`, which today has exactly the four parameters DATA-IN-100 names. In particular, nothing here re-asks for document-type classification — `DocumentTypeClassifier` already produces the `DocType` that selects which anatomy DATA-IN-130 versus DATA-IN-135 applies, and I have treated it as an input, not a gap (see tensions for where it is too weak to lean on).

DATA-IN-110 already establishes the pattern of a run report that names each problem file and the reason. DATA-IN-175 deliberately does not duplicate it: 110 covers files that could not be parsed at all, 175 covers files that parsed fine but yielded nothing for a field. I have marked 175 as refining 110 so the Systems Engineer can decide whether both findings belong in one run report artifact or two.

CORE-200 already asserts that clustering groups documents "by shared acquisition-requirement content." That sentence is the need statement in requirement form, and I have not restated it. What is missing is any requirement that gives "requirement content" an operational meaning — DATA-IN-140, 145 and 150 supply it, and they are written as constraints on the text handed to CORE-200, not as a second clustering requirement.

CORE-240 and NFR-510 already forbid LLM calls and outbound network traffic on this path, so I have not written "the extractor uses no LLM" as a requirement anywhere. Nine of the ten proposals are deterministic rule work that raises no question there at all; the tenth (DATA-IN-160) inherits those two constraints and re-observes them in its test procedure rather than re-asserting them.

One further honest note on coverage: `src/Naadap.Core/Tokenizer.cs` already performs a crude, token-level version of boilerplate suppression — its stoplist drops "shall", "contractor", "requirement", "scope", "task", "objective", "performance" and others. That is a partial, accidental head start on DATA-IN-145 and 150, and it is also a direct conflict with DATA-IN-140. See tensions.

**Tensions flagged:** Nine places where this need pulls against something. None of these are hypothetical; each is grounded in code or fixtures I read.

1. The existing tokenizer destroys the signal DATA-IN-140 depends on. `Tokenizer.cs` drops "shall" as a stopword. DATA-IN-140 needs "shall" as the primary task marker. These are compatible only if task-statement extraction runs during ingestion, before tokenization, and the extracted statements are carried on the record rather than recovered later from the token stream. If the Systems Engineer sequences it the other way, DATA-IN-140 cannot be implemented at all. The same stoplist also drops "scope", "requirement", "task" and "objective" — the exact words DATA-IN-130's synonym table matches headings on — so heading detection must also run pre-tokenization. This is a sequencing decision, not a preference, and it should be settled in the SDD before any of these are implemented.

2. DATA-IN-130 and 135 inherit `DocumentTypeClassifier`'s weakness. Classification today is a literal token match on "sow", "pws", "cdrl", "sources sought" or "open source", against the filename first and then the first 2000 characters; everything else returns `Unknown`. `v1-04-fusionsupport-sow.pdf` classifies as SOW only because the filename we gave it says so — its own text opens "STATEMENT OF WORK", two words that the classifier's single-token rules do not match. A real GFI document named `N0001926R0043_AttachmentJ-1.pdf` would return `Unknown` and receive no section index, no task statements, and no constraint attributes. My proposals are gated on document type and are therefore only as good as that gate. Strengthening the classifier is real work that belongs to whichever need statement owns document identification; I have not proposed it here because it is outside this band, but it is a prerequisite and should be tracked as one.

3. DATA-IN-150 couples every document's features to the whole corpus, which strains CORE-210 and NFR-520. Corpus-frequency boilerplate suppression means adding or removing one document changes the clustering text of all the others. That is the correct behavior for the method, but it has two consequences worth stating plainly: the pipeline can never be made incremental or streaming without breaking CORE-210's reproducibility bar, and NFR-520's five independent replicas reproduce each other only if every replica sees a byte-identical input directory. Today NFR-520 is satisfied trivially because nothing is corpus-dependent. After DATA-IN-150 it is satisfied conditionally. TP-520 should be re-read against this before DATA-IN-150 is implemented.

4. DATA-IN-160 is the only proposal that spends compute, and CORE-220's budget is 1 core and 2GB. A character CNN or a small int8 ONNX encoder over 20 documents fits inside 30 minutes at that tier; per-sentence inference with a general transformer does not. The requirement is written implementation-neutral on purpose, but the Systems Engineer should treat the CORE-220 budget as the binding constraint on model selection, not as something to be verified afterwards. TP-160 re-observes CORE-220 for exactly this reason.

5. DATA-IN-160 also sits close to a line CORE-240 draws. CORE-240 requires zero LLM SDK references and zero calls to a model-serving endpoint anywhere in the core path, "verified by inspection of the module's dependencies." A vendored ONNX classifier is not an LLM and makes no call, but a reviewer performing TP-240 will find `Microsoft.ML.OnnxRuntime` in the dependency manifest and has to be given the reason it is not a violation. That belongs in DELIV-970's algorithm documentation and in DELIV-920's dependency justification, and it should be written before TP-240 is re-run, not after a reviewer raises it.

6. I did not propose NAICS prediction, and the client asked for it. This is a deliberate refusal, not an omission. FAR 19.102 makes NAICS selection the contracting officer's designation and it sets the size standard that determines who may compete. references/ai-boundaries.md reserves set-aside and socioeconomic program choice to the human decider and permits the tool only to supply evidence toward it. A field labeled as the document's NAICS, produced by a model, carried into a consolidation recommendation, is closer to originating that determination than I am willing to write. PSC carries no such consequence — it is a reporting and category-management code under FAR 4.606 — so DATA-IN-160 predicts PSC only. references/vehicle-matching.md independently supports this: orders under multiple-award IDIQs inherit the IDIQ's NAICS in FPDS, so order-level PSC is the reliable code and a predicted NAICS would be the weaker field anyway. If the client wants NAICS prediction regardless, it should be a separate, explicitly-labeled advisory field with the reserved-decision caveat attached, and the client should make that call knowingly.

7. DATA-IN-170 captures constraint attributes but nothing yet says they are excluded from the similarity feature space. references/vehicle-matching.md calls for zero-weighting Security, Travel, GFP and Period sections for topical similarity while keeping them as structured attributes. Capture is DATA-IN's job and is proposed here; the weighting decision is CORE's and I have not written a requirement outside my band. As it stands, implementing DATA-IN-170 alone would populate the structured fields while leaving the same text in the clustering stream, which delivers none of the benefit. A CORE-band item asserting the section-weight profile is needed to close this, and the two should be implemented together.

8. DATA-IN-155's vendored tables have effective dates, and NFR-500 freezes them into the image. The PSC Manual's April 2024 revision restructured 68 IT service codes into 40 new ones. A document written against the old edition states a code that a container carrying the new table will reject as invalid, and DATA-IN-155 will then report it as absent rather than as stale. The vendored table must therefore be version-stamped in the run manifest, and the DATA-IN-175 report should be read with that in mind. This is a small thing that becomes a large thing when GFI arrives carrying older documents.

9. A finding from the real corpus that changes how much DATA-IN-145 is worth. The twenty reference documents are not uniform: `v2-01-sbrac-vi-solicitation.pdf` extracts to roughly 1.36 million characters with 333 clause-number hits, `v3-06-firepumps-r38-solicitation.pdf` to 640,000 with 69, while `v1-04-fusionsupport-sow.pdf` extracts to 83,000 with zero clause numbers and zero DID citations. Clause stripping therefore does almost nothing to the SOW and CDRL attachments and a great deal to the three or four full solicitations. The client should understand that DATA-IN-145 is not a general-purpose cleanup — it is a targeted fix for solicitation-shaped documents, and the residual problem it does not touch is document-length imbalance of roughly sixteen to one, which will distort TF-IDF weighting regardless of how much boilerplate is removed. That is a CORE-band normalization question, and it is arguably a larger accuracy lever than anything in this band. I am flagging it rather than proposing it out of band.

## Need 5 — small-business impact / feeds a determination

**Coverage note:** Three parts of this need statement are already covered and I am not restating them. (1) The existence of a reviewable per-run bundle that a government evaluator reads is OUT-440; NFR-540, NFR-550, NFR-570 and OUT-490 attach to that bundle rather than create a second one. (2) Document-level traceability already exists: DATA-OUT-300 requires each candidate to carry "the set of source documents that contributed to it," and VehicleRecommender.cs already emits ContributingDocuments. NFR-560 does not restate that — it refines it from filename granularity to a resolvable span or knowledge-base row, which is the granularity the need statement asks for ("back to a document span or a knowledge-base row"). (3) The no-LLM-in-core constraint that keeps the recommendation path deterministic and inspectable (CORE-240) already does part of the "never substitute for a determination" work, since an inspected, non-generative path cannot write determination prose; NFR-550 covers the remaining exposure, which is the optional LLM summarization step CORE-250 permits. Nothing in the current RTVM mentions small business, FAR Part 19, approval authority, decision-support labeling, or recommendation completeness — OUT-450 through OUT-490, NFR-540 and NFR-550 are genuinely new ground, and OUT-450/460/470/480 all refine DATA-OUT-300's result record rather than replacing it. One honest caveat on OUT-490: DATA-IN-110 already establishes the "flag it, don't drop it, and say why" pattern for skipped inputs; OUT-490 applies that same pattern to an under-evidenced recommendation, so it is a sibling of an existing idea rather than a new one, but DATA-IN-110 is about input files and says nothing about recommendation completeness.

**Tensions flagged:** Five real conflicts, none of them cosmetic.

1. Nothing in the codebase can populate these fields today, and OUT-490 will say so out loud. IngestionRunner.cs builds a DocumentRecord from four fields only (text, type, filename, date) — no PIID, PSC, NAICS, office code or section structure is extracted anywhere, DocumentTypeClassifier.cs returns Unknown for anything outside five literal tokens, and there is no vehicle or incumbent knowledge base in the repository at all. On the current build, every field OUT-450/460/470/480 asks for resolves to `unknown`, so OUT-490 marks every recommendation `incomplete`. That is the correct and honest outcome, but it means these requirements are blocked on two capabilities that no RTVM item yet covers: structured field extraction at ingest, and a vendored knowledge base. If the client wants them Approved rather than Blocked, those two predecessors need IDs of their own in the DATA-IN and CORE bands.

2. Incumbent business size and set-aside history do not live in the documents — they live in FPDS/USAspending/SAM.gov. NFR-500 and NFR-510 forbid fetching them at run time, so they must be vendored into the image, which makes them stale by construction (NFR-570's version stamp exists because of this) and adds weight against CORE-220's 30-minute, 1-core/2GB budget. A national incumbent-size table is large; the knowledge base will need to be scoped to the corpus or to Navy offices, and that scoping is itself a documented decision a judge may probe.

3. "Every consolidation recommendation" needs a definition the current code does not have. VehicleRecommender.cs maps one cluster to one candidate and scores singleton clusters 1.0 "by convention," which puts one-document clusters at the top of the ranked list. A one-document cluster is not a consolidation at all — there is nothing to consolidate — so a small-business impact note on it is meaningless. I have scoped OUT-450/460/470 to recommendations covering two or more member requirements, which means the ranking bug is now load-bearing for compliance, not just for precision@5: while singletons rank first, the top of the list carries no impact notes and OUT-490 marks it accordingly. Fixing the singleton scoring is a prerequisite to these requirements being worth anything.

4. NFR-550 can abort a run that CORE-250's optional LLM step poisoned. The core path cannot originate determination prose, but a summarization model can and will produce "necessary and justified" style sentences. I have written the gate as fail-the-run because a silently-stripped artifact is worse than a failed one, but the client should see the trade: a demo-day run could abort on a phrase the model chose. The alternative — drop the LLM artifact and finish the run — is defensible too and should be a deliberate client decision, not an implementation accident.

5. NFR-570's run timestamp puts a per-run-varying field in manifest.json, which CORE-210's reproducibility bar must not be read as forbidding. TP-210 compares the top-5 candidate list, not manifest bytes, so there is no conflict as written — but any future "diff the manifests" shortcut for CORE-210 or NFR-520 would break on the timestamp and on nothing else. Worth stating in the SDD before someone writes that test.

One boundary risk to flag rather than hide: OUT-480 has the tool name an approval authority, which is one step closer to acquisition-strategy reasoning than the other items. It is defensible only because the selection is a published lookup on two shown inputs (NMCARS 5207.107-2/-3 against estimated value and bundling indicator) with the thresholds held in the versioned knowledge base, and because the field says which determination the evidence would feed rather than that a determination is warranted. If it ever starts selecting on facts the tool estimated rather than extracted, it crosses the ai-boundaries.md line.
